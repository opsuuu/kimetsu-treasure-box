# 商品圖片儲存遷移至 Cloudflare R2 規劃

**文件版本：** v1.0
**狀態：** Draft
**適用專案：** 富岡義勇 × 胡蝶忍周邊圖鑑平台
**後台應用程式：** `apps/admin`

> 本文件補充並**取代**《周邊圖鑑平台後台管理系統規格書》中關於圖片儲存的描述（原 §3.2、§20.1「Supabase Storage」）。資料庫與 Auth 仍使用 Supabase，僅**圖片檔案**改存 Cloudflare R2。

---

# 1. 文件目的

定義後台商品圖片（封面圖與其他圖片）從 Supabase Storage 遷移至 Cloudflare R2 的架構、設定與實作規格。

---

# 2. 背景與決策

## 2.1 為什麼遷移

- Supabase 免費版限制：檔案儲存 1 GB、流量（egress）5 GB／月，圖鑑正式上線後圖片會最先觸頂。
- Cloudflare R2 免費額度：儲存 10 GB、**egress 永久免費**，且可搭配自訂網域走 CDN。
- 專案將正式發佈於 Cloudflare（已購入網域 `giyushino.com`，規劃前後台部署於 Cloudflare Pages）。

## 2.2 選定方案：Pages Function + R2 綁定

圖片上傳透過 Cloudflare Pages Function（`functions/api/upload.ts`）以 R2 binding 寫入。

**為何需要伺服器端中間人：** R2 的 S3 金鑰為機密，不能置於 client-side 前端（瀏覽器可見）。因此「寫入（上傳／刪除）」需經過伺服器端驗證；「讀取」則公開直連 R2，不經中間人。

**為何選 Pages Function 而非 Supabase Edge Function（presigned URL）：**

| 比較項         | Pages Function（採用）  | Supabase Edge Function  |
| -------------- | ----------------------- | ----------------------- |
| R2 API Token   | **不需要**（binding 授權） | 需要，且須保管          |
| 部署契合度     | 高（全站在 Cloudflare） | 中（多跨一個平台）      |
| 本地開發       | `wrangler pages dev`    | `vite` 照舊             |

# 3. 架構總覽

```text
[瀏覽器 / admin 前端]
   │  1. 帶 Supabase JWT，POST multipart(file, characterSlugs)
   ▼
[Pages Function  /api/upload]
   │  2. 驗證 JWT（Supabase /auth/v1/user）
   │  3. resolveItemFolder 決定 key 前綴
   │  4. env.BUCKET.put(key, file)   ← R2 binding，無金鑰
   ▼
[R2 bucket: giyushino-images]
   │
   ▼
[公開讀取] https://<public-url>/giyu/....jpg   ← 訪客直連，免 egress 費
```

# 4. 技術設定

## 4.1 wrangler 設定

`apps/admin/wrangler.jsonc`：

- `pages_build_output_dir: "dist"`
- `r2_buckets` 綁定：`binding: "BUCKET"` → `bucket_name: "giyushino-images"`

`wrangler pages dev` 的 R2 binding 僅支援 **local 模擬儲存**（不支援連雲端真正 bucket）。因此本地上傳的圖片存在本機模擬 store，回傳的 r2.dev 網址在純本地開發時不會顯示該圖；需視覺驗證圖片載入時，部署 Pages preview 或正式環境。

## 4.2 package.json scripts

| script   | 指令                 | 用途                          |
| -------- | -------------------- | ----------------------------- |
| `dev`    | `vite`               | 純前端開發（不需上傳時最快）  |
| `dev:cf` | `wrangler pages dev` | 含 Function／R2 的完整本地環境 |

`wrangler` 加為 devDependency。

## 4.3 環境變數

**本地** `apps/admin/.dev.vars`（需 gitignore）：

```text
SUPABASE_URL=<專案 URL>
SUPABASE_ANON_KEY=<anon key>
PUBLIC_R2_URL=https://pub-441a0377575f42dcb1a0f836da158efc.r2.dev
```

**正式**：上線時於 Cloudflare Pages 後台設定同名變數。

# 5. 上傳端點規格 `/api/upload`

| 項目     | 規格                                              |
| -------- | ------------------------------------------------- |
| 路徑     | `POST /api/upload`                                |
| 請求格式 | `multipart/form-data`：`file`、`characterSlugs`   |
| 驗證     | `Authorization: Bearer <supabase access_token>`   |
| 驗證方式 | 打 Supabase `/auth/v1/user`，200 才放行           |
| 儲存 key | `{folder}/{timestamp}.{ext}`                      |
| 成功回應 | `{ url: string }`（公開圖片網址）                 |
| 失敗回應 | 401 未授權／400 缺檔／500 寫入失敗                 |

---

# 6. 前端服務介面 `storage.ts`

`uploadItemImage(file, characterSlugs)` 介面維持不變（呼叫端無需調整），內部改為：

1. 取得 Supabase session `access_token`
2. 組 `FormData`（file + characterSlugs）
3. `fetch('/api/upload', { method: 'POST', headers: { Authorization }, body })`
4. 回傳回應中的公開 URL

HTTP 一律使用原生 `fetch`，不引入 axios。

# 9. 安全性

- 上傳需通過 Supabase JWT 驗證，未登入無法寫入。
- 未來 3–5 位協作者以 Supabase Auth 帳號控管；停用帳號即切斷其上傳權限。
- R2 金鑰不落入前端，亦不需分發給協作者。
- Public access 僅開放「讀取」，寫入／刪除一律經 `/api/upload`。
